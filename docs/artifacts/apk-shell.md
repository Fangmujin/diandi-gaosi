## 2. 构建流程说明

手动 APK 流水线（无 Gradle）：

1. `aapt2 compile` 编译资源。
2. `aapt2 link` 生成 `build/base.apk`。
3. `javac` 编译源码（PowerShell 5.1 GBK stderr 死锁问题通过 `build/javac_step.ps1` 子进程规避）。
4. `d8` 生成 `build/dex/classes.dex`。
5. `build/inject_step.py` 注入 dex、按 ABI 注入 `native/prebuilt/<abi>/*.so`（STORED + 755），并补齐 zip 目录条目。
6. `zipalign`。
7. `apksigner sign`。

## 4. 已验证的坑与修复

### 4.1 javac @argfile 路径被转义
- 现象：`@javac_args.txt` 里的反斜杠被当成转义符，路径被吃成 `C:Users28928...`。
- 修复：`build/javac_step.ps1` 把 argfile 中所有路径用 `-replace '\\','/'` 换成正斜杠。

### 4.2 PowerShell safe-delete 钩子阻断 `Remove-Item`
- 现象：`build.ps1` 清理中间目录时被安全删除钩子拒绝。
- 修复：改用 .NET `[System.IO.Directory]::Delete($d, $true)`。

### 4.3 `build.ps1` 曾在 javac 失败后继续打半成品包
- 现象：javac 报错但 classes 目录还有上一轮旧 class，d8 继续执行。
- 修复：`build.ps1` 现在检查 `javac.log` 必须包含 `exit=0`，否则直接 throw。

### 4.4 单线程 HTTP 服务 + WebView 预连接导致冷启动极慢
- 现象：页面 `readyState` 长期 `loading`，9 MB runtime 资产要 1-2 分钟；28 MB PLY fetch 117 秒。
- 原因：WebView 会预开 2-3 条空闲 socket，单线程 `HttpServer` 串行处理，每条空闲 socket 都要等 `SO_TIMEOUT` 才释放。
- 修复：`app/src/com/diandi/gaosi/HttpServer.java` 改为 `ExecutorService` 线程池（8 条），并加 `BufferedInputStream/BufferedOutputStream`、`TCP_NODELAY`。

### 4.5 查看页“No parser found”
- 原因：直接喂 PLY 给 PlayCanvas；需要 PLY → GLB（KHR_gaussian_splatting）。
- 修复：恢复 `app/assets/runtime/dist` 与 `lib` 下的 splat-transform 运行时，`app/assets/js/viewer.js` 中 `plyToGlb()` 转 GLB 后使用 `pc.Asset('model.glb', 'container', ...)` + `instantiateRenderEntity()` 渲染。

### 4.6 `adb shell screencap` 在 Git-Bash 下路径被转义
- 修复：执行前 `export MSYS_NO_PATHCONV=1`。

### 4.7 固定抽帧数导致 SfM 视差不足（app 侧真 bug）
- 现象：8.7s 素材固定抽 40 帧 → 相邻帧间隔 0.2s → SfM 报 `no valid initial image pair`、退出码 7。
- 定位：在设备上手工 exec `libiii_sfm.so` 复现，拿到引擎原话
  `{"stage":"error","message":"no valid initial image pair (need more parallax / more frames)"}`。
- 修复：`PipelineManager.paramsFor()` 新增 `frameSpacingSec`（快档 0.75s / 精档 0.55s）与 `minFrames`；
  `frameBudget()` 按时长折算帧数并夹在 `[minFrames, params.frames]`；`FrameExtractor.duration()` 新增取时长接口。
  改动后 8.7s 视频抽 12 帧，SfM 一次跑通并产出 COLMAP。

### 4.8 用 bbox 定相机距离会被远场飞点带偏
- 现象：3DGS 训练产物里有 1~2% 的远场飞点（floater），它们能把包围盒对角线撑大 7 倍以上；
  按 `getWorldBounds()` 算相机距离会把主体缩成一个小点。
- 修复：`app/assets/js/viewer.js` 新增 `plyFraming(buf)`——解析 PLY header 得到 stride 与 x/y/z 偏移，
  采样最多 20000 个点算**质心 + p95 半径**，`cam.dist = p95 × 2.6`；bbox 仅作兜底并乘 0.35 收缩。
- **系数不能用"半径 × 固定倍数"**，要按 FOV 分轴算取 max：竖屏视口的水平 FOV 比垂直窄得多，
  固定倍数会水平裁边。实现里 `rH = p95(√(dx²+dz²))`（绕竖直轴旋转不变）、`rV = p95(|dy|)`，
  `dist = max(rH/(fill·tan(fovx/2)), rV/(fill·tan(fovy/2)))`，`fill = 0.9`。
  这样竖屏/横屏/分屏都不会裁。
- **离线验证**（不需要设备）：用 `cameras.bin` 的真实内参 `f=1362.967`、视口 640×1136、
  绕 y 每 45° 共 8 个方位角做 pinhole 投影，主体 = 到质心距离 ≤ p95 的 5732 个点：

  | dist | 倍率 | 主体入画 | 投影占宽(未截断) | 占高 |
  | --- | --- | --- | --- | --- |
  | 3.61 | 2.60×R | 94.1–99.7% | 143–168%（裁） | 90–95% |
  | 4.17 | 3.00×R | 96.0–99.8% | 125–143%（仍裁） | 77–81% |
  | **5.09** | **3.66×R** | **99.3–100%** | 101–115% | 62–66% |

  与 native-sfm 独立复算的入画率/高占比逐项吻合（94.1% vs 94.3%、89.9–95.5% vs 89.4–96.7%）。
  注：app 实际 canvas 是 411×914（aspect 0.45），最终距离约 6.4，主体占宽 ~80%、占高 ~50%——
  竖屏视口装各向同性物体无法宽高同时撑满，属几何限制。想顶满画面可把 `fill` 调到 1.0。
- **x/y/z 的字节偏移必须按 header 顺序累加，不能硬编码**：x/y/z 落在属性末尾只是 brush 当前导出顺序，
  SH degree 一变（`f_rest_*` 从 9 个变 24 个）或顺序一调，写死的偏移会读到 `scale_*`/`f_rest_*`，
  而且不报错、只是悄悄框错地方。实现里按 `stride += 类型大小` 累加并顺带记录类型，
  `double` 也能正确读取。采样为等间隔（`step = count/20000`），不取前 N 个（splat 按训练顺序/空间分块排列，
  取前 N 会偏在物体一角）。
- 回归测试：`build/test_ply_framing.py`，会构造「x/y/z 置顶」和「x/y/z 置顶 + SH degree 2」两个变体，
  断言质心与 p95 半径不变。当前结果 `RESULT: PASS`（stride 92 → 152 时结果仍一致）。

### 4.8.1 取景算法的三条保证（真机变数下仍然成立）
- **相似变换不变**：整条链路是「质心 → 分位半径 → 按 FOV 反推距离」。点云整体缩放 k 倍时，
  `r_p95` 缩放 k 倍、`dist` 也缩放 k 倍，**取景结果完全不变**。这条是真机能扛住变数的根本原因：
  单目 SfM 的绝对尺度本来就是任意的（由初始两帧三角化归一化定标），真机用户拍的场景尺度
  必然和实验室数据集不同，但构图不会因此跑偏。**不要引入任何依赖绝对尺度的常数**（见 §4.8 里
  被否掉的 `p95 × 2.6`）。
- **不读 `scale_*` / `opacity`，所以躲开了单位坑**：PLY 里 `scale_0/1/2` 存的是 **log(scale)**，
  `opacity` 存的是 **logit**（未过 sigmoid，原始范围会出现负值）。还原物理值要 `exp()` / `sigmoid()`。
  取景只用位置，因此完全不受影响。**若将来任何代码要读这两个属性，必须先还原**，否则会像
  native-brush 那样把 log 空间的计数当成世界单位（他已自我纠正：原先"两帧都是 39 个大 splat"
  是单位错误制造的假象，正确图景是渐变——世界单位 >1.0 档约 130–200 个、极端 >1.5 档约 90–100 个，
  占比 0.4%–2.2%，量级结论方向不变但数字已改）。
- **远场 tail 是训练侧的系统现象，不是 SfM 数据的锅**（native-sfm §9.5.5 已推翻早前归因）：
  决定性对照是 11 帧那组 SfM 输入**一个远场点都没有**（radius>3 计数 0，max 仅 1.5142），
  训练后照样长出远场点（max 10.3496）。原始数字：干净输入 SfM max 1.5142 → 训练后 10.3496；
  带离群点输入 SfM max 19.1185 → 训练后 20.8350。
  **口径提醒**：早前我写过的"训练把 floater 推到约 **2.5× 主点云尺度**"是**拟合出来的比值常量，已作废**
  （native-brush 纠正了 native-sfm 的拟合公式与一处算术）。要写就写**实测值**并标注观察性质：
  **≈10 个世界单位（场景尺度约 4 时）**，且注明"实测自 2 组数据，属观察，非定标常量"。
  → 真机上一定也有这么一撮点。p95 分位会丢掉它们；**任何退回 min/max 的兜底路径都会在这里崩，
  务必保持"不用 bbox min/max"这条纪律**。
  **并且不能用库自带的 bound 来替代** —— 见下面 §4.8.1 末尾的「为什么不能用库自带 bound」。
- **渲染侧的 log-scale / logit 还原已核实（不是假设）**：`plyFraming()` 只读位置，不受影响；
  而 PLY→GLB 交给打包进 `assets/runtime/dist` 的 splat-transform 官方库，它是否真的做了还原，
  native-sfm 替我们读了源码确认（`app/assets/runtime/dist/index.mjs` 的 `SplatIterator`）：

  ```js
  const activated = gsplatData.activated;      // GSplatData 默认 false
  if (activated) s.set(sx[i], sy[i], sz[i]);
  else           s.set(Math.exp(sx[i]), Math.exp(sy[i]), Math.exp(sz[i]));
  c.set(0.5 + cr[i]*SH_C0, ..., activated ? ca[i] : sigmoid(ca[i]))
  ```

  全文件只有**一处**赋 `activated = true`，在"由已激活数组构造 GSplatData"的路径（GLB/内部传递）；
  **从 PLY 文件读出来的走 false 分支** → scale 过 `Math.exp`、opacity 过 `sigmoid`，brush 那份
  log/logit PLY 被正确还原。四元数映射也是标准的（`r.set(rot_1, rot_2, rot_3, rot_0)`，w=rot_0）。
- **为什么不能用库自带 bound（写清楚，免得后来的人手痒）**：splat-transform / PlayCanvas **内部**的
  bound 与质心计算是**含 splat 半径**的（`2 * (activated ? scale : Math.exp(scale))`，另有
  `1/(1+exp(maxScale))` 加权的质心）。改用库自动算的 bound 取景，就会踩到我们测过的那个膨胀
  （11 帧 bbox 对角线 22.49 → 114.42，约 **5×**；44 帧 41.73 → 87.32，约 2.09×；两份数据的
  放大倍数本身差 2.4 倍）。所以"用位置分位数"这条纪律的完整表述是：
  **取景只能由 `plyFraming()` 出，不要用 `getWorldBounds()` / 库自带 bound。**
  当前代码里 min/max 分支已删除，是结构性保证；`viewer.js:289` 的兜底分支**目前不可达**
  （只有 `plyFraming()` 返回 null 才会进），已加 `console.warn` 标记，避免静默退化
  ——真机上若看到画面偏远，要先能区分是"p95 没调好"还是"根本没走 p95"。
- **调档（p92/p95/p99）可以纯粹按占宽决定，不用顾虑 tail 混进来污染分位数**——有量化保障。
  native-sfm 用同一口径（半径以 SfM 点云质心为原点）把 **2 个数据集 × 2 个步数 = 4 组**都算了：

  | | splats | p90 | p95 | p99 | max | **max/p95** | **max/p99** |
  |---|---|---|---|---|---|---|---|
  | 11 帧 / 2000 步 | 6,033 | 1.371 | 1.485 | 2.278 | 10.350 | 6.97× | 4.54× |
  | 11 帧 / 6000 步 | 64,676 | 1.452 | 1.592 | 2.834 | 19.927 | **12.52×** | 7.03× |
  | 44 帧 / 2000 步 | 21,680 | 1.719 | 1.938 | 4.189 | 20.835 | 10.75× | 4.97× |

  **四组全算上，余量下限是 max/p99 ≥ 3.94×、max/p95 ≥ 6.97×。**
  （口径订正：我早前写的"floater 在 p99 之外还有 **4.5–5 倍**"只是 2000 步那两组的范围，已作废。）
  → **哪怕训练拉到 6000 步，飞点也进不了取景统计**。所以 §4.8.2 的调档（p92/p95/p99）

  **远场点涨得比模型规模快得多（15× vs 6–11×）。**

  **⚠ 由此推出的"降步数比调取景更治本"已被 native-sfm 撤回，不要写进产品决策。**
  原推论是用**全局远场计数**（39 → 12,771，327×）推观感，属口径错配——全局计数涨 ≠ 画面变脏。

- **画面脏不脏要看视锥投影，不看全局计数。** native-sfm 用 `native/sfm/tools/occlusion_stats.py`
  按 `viewer.js` 的构造式重建取景相机（yaw30/pitch18、fill 0.9、fov 45° 竖直、`tX=tan(fov/2)·asp`），
  竖屏 asp=0.45 下做了视锥投影计数：

  | 组 | 视锥内 r>3 | **主体前（会挡）** | 占 splat | 其中不透明>0.5 |
  |---|---|---|---|---|
  | 11帧/2000 | 6 | 9 | 0.15% | 0 |
  | 44帧/2000 | 103 | 113 | 0.52% | 8 |
  | 11帧/6000 | 36 | 113 | 0.17% | 0 |
  | 44帧/6000 | 2,638 | 279 | 0.20% | 4 |
  | 44帧/13000 | 4,253 | 726 | 0.24% | 2 |

  两条结论：
  1. **"分位数框住的圆柱" ≠ "视锥"**，别混用。竖屏下视锥在主体深度处的竖直半高 ≈ 5.18，
     而 v95 只有 1.68 —— 视锥比那个圆柱大得多，所以**远场点确实进画面了**（2,638 / 4,253 个）。
     native-brush 的"圆柱框内 r>3 = 0"是对的，但只能读作"框内为 0"，**不能读作"画面里没有远场点"**。
  2. **但进画面 ≠ 挡主体**：真正落在主体与相机之间的只有 **0.15%–0.24%**，不透明>0.5 的是个位数。
     → **取景按分位数走这条路线没有被动摇**；"加长训练让画面变脏"不成立。
- **视锥计数对屏幕比例敏感**（`dist` 随 asp 变：竖屏 ≈12.4，方屏 ≈5.6）。
  所以查看页日志除分位数外还打了 `dist` 与 `asp`（`[framing-fit]`），
  否则真机数字无法与 native-sfm 的 occlusion_stats 对齐。

### 4.8.2 p95 调档的量化判据（不用靠肉眼）
真机第一眼若觉得主体大小不合适，按「**p95 壳占画布宽度的比例**」判，而不是凭感觉：

> **方向修正（原版写反了，已改）**："主体偏小 → 往 p99 挪" 是**错的**，两个理由：
> ① 几何上反了——分位越高 → 半径越大 → 相机越远 → 主体越小；
> ② 直觉上更错——p99 落在半径长尾最尖端，相机被推到极远（**生产口径**：快档基线
> q=0.99 `dist=30.48` vs q=0.95 `dist=11.87`，远 **2.57×**；加正则后 17.19 vs 10.04，
> 仍远 **1.71×**），主体小到不可用。
> 原版是按"p95 被污染导致偏大"这一个成因假设写的，**只在污染时成立，参数没调好时是反的**；
> 现在按几何方向重写，不按成因假设。
> （② 的原论证用"p99 失效阈值 1% < 实测远场占比 4.4%"，**该论证已随 §4.8.3 撤回**——
> 远场占比不可测。结论保留，理由换成上面的直接量。）

**方向关系（唯一需要记住的一条）**：

> **分位越高 → 半径越大 → `dist` 越大 → 相机越远 → 主体越小。**

- **主体偏小 / 画面大量留白**（想拉近）→ **降低**分位：p95 → **p92 / p90**
- **主体过大 / 边缘裁切多**（想拉远）→ **提高**分位：p95 → **p96 / p97**

**可调范围是 p90 ~ p97，p99 不可达**（`FRAMING_Q_MIN/MAX`，viewer.js）。理由只用不依赖阈值常数的
直接量：同一份 PLY 上 q=0.99 → `dist=30.48`，q=0.95 → `dist=11.87`（生产口径快档基线），
相机距离 2.57 倍，主体按 `1/dist` 缩小到不可用。
**（原理由"失效阈值 1% < 远场占比 4.4%"已撤回，见 §4.8.3。）**
（⚠ `viewer.js` 里那句注释仍是旧口径的 `31.86 / 12.47`，**结论同向、倍数 2.6 vs 2.57**，
下次打包时一并更新；不为此单独重打。）

**降档触发条件：不设自动触发，只能人工判断。**
> 旧写法是"远场占比超过 `1-q`（即'已用%' > 100%）时才降 p90"，**已作废** —— 远场占比不可测
> （§4.8.3.3），这个表达式永远不会被正确求值，照它实现只会写成死代码。
> 替代：**真机上肉眼看主体是否偏小**，是则人工把 q 往 p92/p90 调。
> 另注：**"主体偏小"也可以动取景 `fill`（拉近相机）解决，不一定动分位** —— 这两件事要分开。

**判据用「入画率」，不要用"p-q 壳占宽"** —— 后者是**自指**的：`dist = r/(fill·tan)`，
按定义 p-q 壳必然占据 `fill = 0.9`，永远是 90%，测不出任何东西。可用的量是
**入画率 = 投影后落在画布内的采样点占比**（native-sfm 同口径）：

- 甜区：**97%–98%**（剩下 ~2% 是永远框不进的 floater 天花板）
- **< 95%**（裁切多）→ 相机太近 → **提高**分位（p97/p99）
- **≈99–100% 但主体明显小、留白多** → 相机太远 → **降低**分位（p92/p90）

native-sfm 实测（411×914 画布、采集 fovx 26.44°）：11 帧 `dist=5.065` → 97.4–98.1%；
44 帧 `dist=7.938` → 97.5–98.4%。画布宽高比不同时绝对值会变，但这条判据是相对的，不变。
（**这两组是旧口径桌面产物**；生产口径的数见 §4.8.3.5，判据形状一致、绝对值要换。）

**分位默认值按档位取**（`framingQuantile()`，viewer.js）：

| 档位 | 步数 | 分位 | 定档依据（**默认视角 yaw=30** 的入画率；**生产口径**，2026-10-15 重算） |
| --- | --- | --- | --- |
| 快档 | 6000 | **p95** | 基线 **97.54%**、加正则 **98.76%**；q=0.90 为 96.06% / 96.47% → p95 优 |
| 精档 | 13000 | **p95** | 基线 **97.92%**、加正则 **98.83%**；q=0.90 为 96.10% / 97.14% → p95 优 |

（旧依据 97.58% / 97.03% 来自**二进制默认参数**产物（res1920/sh3/refine200/growth15000），

改一行常量即可分开，不用重新设计。**精档一度改过 p90，已回退**：默认视角下精档 q=0.90 入画率
96.10%（生产口径；旧口径写的是 95.51%），明显差于 q=0.95 的 97.92%，收益没兑现、代价先付。

代码里顺带打了诊断日志（`[framing]` 分位数串 + `[framing-fit]` 取景结果），
真机上直接抓这两条就能判断取景有没有跑偏，不用等截图。
`[framing-fit]` 一次打出**四套尺寸**，因为 asp 直接决定 dist、也决定巨型 floater 落在相机前面
还是后面（native-sfm 的雾团分析对 asp 极敏感，竖屏 `dist≈10–12` 而方屏 `dist≈4.5–5.6`）：

| 字段 | 含义 | 为什么单独打 |
| --- | --- | --- |

**✅ 成立：日志打的 asp 可能和取景用的不是同一个。**
取景时若 canvas 尚未完成布局，`clientWidth=0` → 走 `graphicsDevice` 兜底，两者可能不同；

**❌ 撤回：~~`FILLMODE_FILL_WINDOW` 撑满整窗 → 顶栏盖住主体顶部~~。**

- 竖屏 asp=0.45 时 `tX = tY·asp`，水平 FOV 比竖直窄得多，**取景是水平约束绑定**
  （44帧/6000：`dH=12.47` vs `dV=4.30`，差 2.9 倍），竖直方向留了约一半空白；

- 竖屏下要让竖直约束绑定，需要 `rV/rH > 1/asp = 2.22`（主体比宽高 2.2 倍还高），
  现有三组是 0.716–0.857，差得远。

  方屏（asp=1.0）下阈值降到 `rV/rH > 1`，那时这条才会真咬人；查看页目前是竖屏。

量不到高度时退化为 1，行为与改动前一致。`[framing-fit]` 会打印 `inset` 与 `visFrac` 供核对。

native-sfm 用 411×914 画布、保持采集 fovx 26.44° 复算过两份数据集，落在我们这个口径下是
11 帧 `dist=5.065` → 入画 97.4–98.1%；44 帧 `dist=7.938` → 入画 97.5–98.4%。
画布宽高比不同时绝对值会变，但"≈90% 占宽"这个**相对判据不变**。

**取景分位数必须现算于最终 PLY，不能外推。** 实现上就是这样：查看页 `fetch('/model/<id>.ply')`
拿到 `final.ply` 的字节后立刻 `frame = plyFraming(buf)`（`viewer.js:62-76`），质心与分轴 p95 都从
**这份 PLY 的位置属性**当场算出来——不从 SfM 点云推，也不用任何常量倍率。

这条不能省，native-brush 用 6000 步实测推翻了"可以外推"的可能：

| | 2000 步 | 6000 步 |
| --- | --- | --- |
| 11 帧 max 半径 | 10.35 | 19.93（**+93%**） |
| 44 帧 max 半径 | 20.84 | 26.51（+27%） |
| 44 帧 splat p99 / SfM p99 | 2.06× | **3.31×** |
| 取景放大倍率（11 / 44 帧） | 5.09× / 2.09× | 2.23× / 2.52× |

结论：**分位数对"极少数飞点"免疫，但对"训练步数"不免疫。** 包络随训练持续外扩，连"同一数据集只换步数"
都能让放大倍率从 5.09× 掉到 2.23×。所以：
- 按 p95 取景的**方向对**（比 min/max 稳得多），但**必须用最终 PLY 实测的 p95**；
- **`--total-steps` 是产品参数不是内部细节**：步数 3× → PLY 体积 6.3×、远场占比 1.83%→4.39%、包络 +27%。
  当前默认档位是**快档 6000 步 / 精档 13000 步**（`paramsFor()`），精档已超出 native-brush 实测过的范围。
  **改默认步数就要按新步数重新标定占宽，不能假设入画率不变。**
- 一个对硬编码有利的观察：训得越久跨数据集差异越小（6000 步时 11/44 帧收敛到 2.23× / 2.52×，
  2000 步时是 5.09× / 2.09×）。但我们仍然读实测分位数，不引入系数。

### 4.8.3 分位数失效阈值 —— **已降级为设计约束，不可当测量判据**

> **本节口径在 2026-10-15 被 native-sfm 撤回并重写。** 原写法把"远场占比 > `1-q` 则 q 分位失效"
> 当成一张可以照着读的仪表（"测一下就知道 p95 破没破"）；撤回的理由不是数字错了，
> 是**这条规则的前提在数据里不成立**。被推翻的过程完整留在 §4.8.3.1–4.8.3.3，
> 以免有人照着旧文案把自动降档重新实现一遍。

#### 4.8.3.1 原规则（从分位数定义推出，数学上严格成立）

> 设远场点占比为 s。第 q 分位落在尾部里 ⟺ `s > 1 - q`。
> 此时"q 分位半径"不再是主体半径而是**尾部半径**，取景距离被自动拉远、主体变小。

| 分位 | 失效阈值（远场占比） | 说明 |
| --- | --- | --- |
| p99 | **> 1%** | 最容易破 |
| p95 | **> 5%** | 当前默认 |
| p90 | **> 10%** | 给长训练留 2 倍余量 |

**但这条推导有一个没写在结论里的前提：远场必须是一个"可分离的点群"。**
只有远场能跟主体分成两簇，`s`（远场占比）才有独立于阈值的定义 —— 否则 s 只能靠"半径 > 某个 k"
来数，而 k 是外部强加的。

#### 4.8.3.2 前提不成立：远场是一条连续长尾，不是一簇

native-sfm 按 log2(半径) 从 p50 到 max 分 12 格统计密度，44 帧 / 6000 步的实测：

```
0.219  0.151  0.074  0.014  0.015  0.015  0.005  0.004  0.003  0.0004  0.0002  0.0001
```

**单调衰减，没有第二个峰。** 半径分布上没有"主体峰 + 远场峰"的双峰结构，
也就是说远场不是从主体里分离出去的一群点，而是同一条分布拖出去的长尾。

#### 4.8.3.3 后果：远场占比测到的是 k，不是数据

前提一破，`s` 就退化为"半径 > k 的点的占比"，值完全由 k 决定。同一份 PLY：

| 阈值 k | 远场占比（44帧/6000） |
| --- | --- |
| 1.5 × p90 | **4.48%** |
| 3 × p90 | **1.22%** |
| 绝对 `r > 3` | 4.39% |

同一份数据，换个 k 差 3.7 倍。**这个测试测到的是 k，不是数据** ——
所以"测一下占比就知道 p95 破没破"根本做不到：你没法在不先定 k 的前提下得到 s，
而 k 一旦定了，结论就已经由 k 决定了。

**推论（写死在代码注释里的总纲）**：
- **由分位数定义的参照集可用** —— 参照集是数据内在的，q 一变它跟着变，值由数据决定；
- **由倍数或绝对阈值定义的量不可用** —— `k×p90`、`r>3` 之类是外部强加的，测出来的值由 k 决定；
- **单档计数不可用** —— 等于把上面任何一种只报了一个点，换档横跳时不知道该信哪档。

入画率、占宽（固定参照集 = 3D 半径 ≤ p95 的点）属第一类；远场占比、`r>3`、`r>3×p90`、巨型片计数属后两类 ——
**后两类只配打日志，不配做判据，也不配做趋势。**

**⚠ 两条纪律是叠加关系，不是替代**（native-sfm 补充，防止这条禁令被用过头）：
**"分位数定义的可用" ≠ "不用做敏感度扫描" —— 分位数本身也是参数（q）。**
雾团指数用的就是分位数定义的参照（"主体前" = `depth < dist − r3_q`），按上面的分界属"可用"，
但它仍有 q 这个旋钮：扫 q=0.90 / 0.95 / 0.99 三档（44帧/6000：0.585 / 0.499 / **0.054**），
**在 q=0.99 上翻了**（从"明显"掉到"隐约"），只是 q=0.99 本身不合理（等于把尾部算进主体）才不影响结论。
所以正确顺序是：**先选"长在数据上"的定义方式（分位数），再按"至少两档"扫一遍。只做第一步不够。**

更准确的分界（不是"分位数 vs 阈值"，而是**有没有自然的枚举序列**）：
- **分位数定义的量**：q 是无量纲的排序位置，取值随 q 连续变化、**可单调枚举**（0.90/0.95/0.99），
  能一眼看出稳不稳；
- **倍数 / 绝对阈值定义的量**：k 带量纲或任意尺度，**没有自然的枚举序列**，换档横跳时无从判断；
- **单档计数**：直接不可信，无论定义方式。

#### 4.8.3.4 降级后的合法用法

- **可以当设计约束**：要让主体占住画幅，取景分位就必须落在你认定的主体群里 ——
  这条仍然指导"为什么不能往 p99 挪"（见下），不依赖任何测量。
- **不可以当测量判据**：不写"占比超 `1-q` 就自动降档"。原代码注释里的
  「远场占比超过 `(1-q)`（即"已用%" > 100%）时才降 p90」这条触发条件已删除 ——
  远场占比不可测，这个表达式永远不会被正确求值，照它实现只会写成死代码。
- **降档只能人工判断**：真机上肉眼看主体是否偏小，是则人工把 q 往 p92/p90 调。
  "主体偏小"也可以靠取景 fill（拉近相机）解决，不一定动分位；
  **"主体过大 / 边缘被裁切"才是提高分位的信号。**

   ⚠ 上面引的"巨型片数"**本身是伪指标，只能用来解释"雾是哪来的"，不能用来决定"删哪些"**
   （native-sfm 自我检验第六类：换一个同样合理的阈值 k，计数就横跳）：

   | 阈值 | σ>3,α>0.5 | σ>2,α>0.3 | σ>5,α>0.7 | σ>1,α>0.5 |
   | --- | --- | --- | --- | --- |
   | 11帧/2000 | 3 | 22 | 0 | 10 |
   | 44帧/2000 | 4 | 23 | 1 | 11 |
   | 11帧/6000 | 0 | 3 | 0 | 0 |
   | 44帧/6000 | 2 | 21 | 0 | 7 |
   | 44帧/13000 | 3 | 22 | 2 | 25 |

   **计数在 0↔25 之间横跳，而这四组阈值都说得通**；唯一稳定的是**排序**。
   这跟 §4.8.3 撤回的"远场占比"是同一类毛病。**所以本节的论证不能建在计数上**，
   建在"累加"这个结构上：任何按单 splat 阈值删的方案都只能削掉最极端那一小撮；
   要把指数从 1.6 压到 0.1 得删掉一大片，届时误删风险已不可接受。**"按视角删"这条路从根上不成立。**
   （**雾团指数本身不是伪指标**：它对"主体前"的 splat 全部求和、不挑，唯一自由参数是"主体前"的分位，
   且 q 在 0.90–0.95 之间稳定（差 <12%），只在 q=0.99 这个不合理取值上翻 ——
   44帧/2000：1.241 / 1.180 / 0.738；44帧/6000：0.585 / 0.499 / 0.054；11帧/6000：0.339 / 0.337 / 0.095。
   **判据用雾团指数，不要用巨型片计数。**）
2. **判据视角相关，而删除是全局的。** 用户能旋转（yaw/pitch 手势）：一个 splat 在 yaw30 是前景、
   在 yaw210 就跑到主体背后。为消掉某一个角度的雾，会把其它角度本来无害的 splat 一起删掉。
   想用"多数方位角都在相机与主体之间"来缓解会撞上内在矛盾 —— 具备该性质的其实是**靠近质心**的点，
   而 #10522 质心半径 8.58、dist≈10–12，只在约一半方位角位于前方，会被这个条件**漏掉**。
3. **误删与误留没有可分离边界。** 真实近距离前景（桌面/地面/手）与巨型 floater 在
   （σ 大、depth 小、alpha 高）特征空间里**重叠**，且**可分离性从未验证过** ——
   这与 §4.8.3 撤回的"远场占比"是同一类前提问题（前提：两类点可分离）。
   判据越往下压，误删真实内容的概率越高。

**取向**：**宁可留一点雾，不要削掉真实内容。** 糊一层是**视觉瑕疵**且可靠旋转/缩放避开；
削一块是**内容缺失**，在任何视角都缺。在误删概率不可估的前提下做**破坏性**操作，不该由我们拍板。

**正确解法在训练侧，且不需要重编译 .so**：`brush-train` 的 `--opac-loss-weight`（默认 1e-9）、
`--scale-loss-weight`（默认 1e-8）两个正则默认小到等于没开，而 prune 三条件
（`alpha_mask` 只删太透明、`scale_mask` 只删太小 `log_scale < -15`、`bound_mask` 阈值
`median_size×10`）正好全漏掉巨型片 —— 所以 σ=10.9/α=0.74 的片一路活到最后。
**这两个是 CLI 参数 → Java 侧 `paramsFor()` 加一行即可，两个 ABI 的 .so 都不用重编译。**

**若将来训练侧方案失效、必须回到 JS 兜底**，只允许这种形态：默认关闭 + 只删极端样本
（同时满足 `σ_max > 3×主体尺度分位` 且 `alpha > 0.5` 且 `占屏比 > 0.5` 且 `depth < 0.5×dist`），
并打日志"删了 N 个 / 雾团指数从 X 降到 Y"，真机肉眼核对后再决定是否放宽。
**绝不做"删 top-N 大 splat"** —— 上面第 1 条已证明它无效。

**⚠ 训练步数与"画面干不干净"无关 —— "要不要为画面干净而调步数"这个问题本身不成立。**
native-brush 用**训练相机位姿 + 深度分桶 + 光栅化 alpha 合成**（与取景完全无关的独立口径）实测：

| | 2000 步 | 6000 步（快档） | 13000 步（精档） |
| --- | --- | --- | --- |
| 前景遮挡 α>0.1 占屏 | 0.271 | **0.269** | **0.271** |
| 前景遮挡 α>0.5 占屏 | 0.113 | 0.157 | 0.160 |

三档**持平**。→ **步数只影响性能/细节，不影响画面干净度**；默认步数不必为雾团问题而改。

**⛔ 上面这两组数（native-sfm 的雾团指数 / native-brush 的前景遮挡）不能互相验证 —— 别写成交叉印证。**
两边**量纲不同**：native-sfm 量的是**屏幕平均新增不透明度**（Σα×占屏比，alpha 加权的连续量），
native-brush 量的是**屏幕面积占比**（前景累积 alpha 超阈值的像素比例）。一个答"平均多浓"，
一个答"多大面积算被挡"。44帧/6000 上 0.399 vs 0.269 **数值接近是巧合**。
**可比的只有趋势与排序，而这两条两边一致，可以定**：
1. **雾团是真的**（非零、在"看得出"量级，不是计数错觉）；
2. **不随步数变差**（0.834→0.399→0.449 vs 0.271→0.269→0.271）→ **"为画面干净而降步数"可以否掉**。

**方法纪律（native-brush 这组数本身就是范例）**：他给了 α>0.1 和 α>0.5 两档，
**数值差 2.4 倍**（确实依赖 k），但"三档持平"在两档下都成立 —— 所以他的结论**过了第六类检验**。
→ **以后报任何参数化量都至少给两档**（k 或 q，视定义方式而定；两条纪律叠加，见 §4.8.3.3）。
上面那张"巨型片计数"表就是只给了一档、
换档横跳 0↔25，被验成伪指标的反例。
（这条同时替代了两条已作废的旧论据，native-brush 已撤回并留档于 `native-brush.md` §5.6.4：

**⚠⚠ 雾团指数单次跑方差极大 —— 这是回退路径的核心风险，别把它当"温和版"。**

→ 回退路径若真要退到 `1e-6`，接受的是**分布**，不是**数值**：
  两次里有两次都干净（0.039/0.051 @1e-5）vs 一次干净一次糊死（0.089/0.929 @1e-6）。
→ **同理，真机单次跑的雾团读数也别当终局判据**：一个角度糊不代表参数失效，

**⚠⚠ 但"差 10×"不能读成"这一档就是不稳定" —— n=2 的极差不是方差估计。**
native-sfm 2026-10-15 补充：每档只跑两次，**两个样本的极差本身波动极大**，即使真实方差很小，
单次极差也轻松到 3–10×。所以"1e-6 两跑差 10×"只能读作"**这两次差了 10×**"；
要断言某档不可复现，**需要 n≥3**。

**⛔ 判据线 0.3 的正确读法（两种错都要避开）**：

1. **别读成"余量够大"。** native-brush 原话"1e-5 离线 6×，即使再来 10× 波动也不会跨"**已由他本人撤回**：

   而且同批数据里**已实测到 10.46× / 10.68× 的倍差** —— **余量比已观测波动还小**。
2. **别读成"判决依赖 0.3 这个取值"。** native-sfm 扫了 5 档线，**判决在 `(0.051, 0.929)` 整个区间内不变**
   （宽 **18×**）：取 0.2 / 0.3 / 0.5 结论都一样。
   - 线 ≥0.93 → 连无正则基线（0.984）都判合格，**判据失效**；
   - 线 ≤0.051 → 1e-5 自己也过线，**判决翻转**。
   端点本身也是 n=2 的点估计，准确读法是"**在已观测取值下，判决对线的取值在 18× 范围内不敏感**"，
   **别当保证区间用**（n 再大只会往大走）。

**⛔ 真机观察三项必须单列，各自独立判，不许合并成"质量分"**（native-brush 收口，native-sfm 从口径边界确认）：

**⛔ 真机单次/单档结果，无论好坏都不能定档，只能触发"补跑"**（native-sfm 立、native-brush 同意）：

### 4.8.5 训练相机口径的入画率（B / D / E / F）—— 与 §4.8.3 的 viewer 口径**不是同一个量**

**⚠ 两套口径各自回答什么问题（别把 26.73% 读成"取景很差"）：**

| 口径 | 数 | 回答什么 | 备注 |
| --- | --- | --- | --- |
| **viewer 相机**（411×914 / fovy 45° / yaw30 / pitch18，`dist` 来自 `fitDistance()`） | 入画率 **97–98%** | "**查看页打开后能看到多少**" | **唯一对应查看页观感的口径** |
| **44 台训练相机**（640×1136 / fov 26.4°） | 入画率 **27–29%** | "**单台训练相机能看到多少**" | 数值**被训练相机的窄 fov 主导**，不是取景缺陷 |

**`dist` 来源确认（team-lead 要求，已做成结构性保证）**：97–98% 那版的 `dist` **就是 `viewer.js fitDistance()` 算出来的值**。
不是"照公式另写一遍"——`tools/ply_quantile_report.mjs` 现在**从 `viewer.js` 里抽出 `fitDistance()` 的函数体原文、
在 node 里用桩对象直接执行**；改了 `viewer.js` 的取景逻辑，脚本自动跟着变，不存在两份实现跑偏的可能。
（切换前后数值逐位一致：`dist=10.0363`，说明此前本就是同一个值。）

**⛔ 入画率绝对值停报 —— Level 由所选分位 q 决定，不是数据的属性**（native-sfm 2026-10-15 修正，§9.5.14.2）：

> **纪律原文：入画率绝对值不作为 Level 报告；只允许报"固定 q 下两模型之间差 n pp"。**

| q | 0.80 | 0.90 | 0.95 | 0.99 |
| --- | --- | --- | --- | --- |
| 入画率 | **91.3%** | 95.9% | **98.8%** | 99.7% |
| 与 q 的差 | +11.3 pp | +5.9 pp | +3.8 pp | +0.7 pp |

q 从 0.80 到 0.99，入画率单调从 91.3% 走到 99.7%，**跨度 8.4 pp 纯由参数决定**。
根因是**自指**：取景相机本身是从点云拟合出来的（质心 → 分位半径 → 距离 → FOV），
点云决定相机、相机再评价点云，入画率天然 ≈ q —— **与已废掉的"占宽 = fill"是同一类（第四类坑）**。
→ **"入画率 98.8%"是伪 Level（换个 q 就是 91% 或 99.7%）—— 绝对值不得作为 Level 引用**；
→ **只报"固定 q 之后两个模型之间的差（n pp）"**；脚本每次输出末尾都打这条警告。

**⚠ "不可互验"的准确理由不是"两个口径不同"，而是"一个由参数决定、一个不由参数决定"**：
viewer 口径的 Level 由 q 决定；训练相机口径的相机位姿与内参都是**给定的**、不含拟合参数，
所以 27–29% 是**数据的属性**。别指望"再对齐一下口径就能互验"——**对不齐，这是性质差别**。

**行定义**（`tools/ply_traincam_framing.mjs`）：
- **B** 基线，相机不动；
- **D/E** 相机**整体外扩** ×1.15 / ×1.30（沿"质心 → 相机"后退，朝向与内参不变，即轨道半径 ×s）；
- **F** 只取"到相机距离最近的那 5%"（贴面子群），相机不动。

⚠ **外扩必须实现成"整体后退"，不能做成"每个 splat 各自沿视线后退"** —— 透视投影是**尺度不变**的，
后者投影像素完全不动、入画率恒等，是个空操作。要产生变化必须改变**视角**。

### 4.12 训练失败归因：口径重写过三次，前两次都被推翻

本轮项目踩过四类坑，它们有**同一个共性：都不会让数字报错，只会让方向反了，或者让结论看着比实际更硬**：

1. **参照盒污染导致方向相反** —— "落在 bbox 内 99.4%"参照的盒子被离群点自己撑大 8 倍，数据越差得分越高。
2. **同一段分析混用两个口径** —— log(scale)：分位数走过 `exp`、阈值表没走。
3. **反向子群抵消成假恒定** —— 91→96 的 1.05× 是 0.48× 和 2.16× 抵消出来的。
4. **判据是死代码** —— 下面 §4.12.1，发生在我身上。

前三类见 native-sfm §9.5.4 / §9.5.5 与 native-brush 文档；第 4 类和它的第二次翻车记在本节。

#### 4.12.1 第一次：判据是死代码

**原做法**（Oct 15 00:02 落盘版本）：

```java
private static boolean looksLikeDatasetContract(String engineMsg, String stderrTail) {
    String t = ((engineMsg == null ? "" : engineMsg) + "\n" + (stderrTail == null ? "" : stderrTail))
            .toLowerCase(Locale.ROOT);
    return t.contains("contains only") || t.contains("colmap dataset directory is required")
            || t.contains("no colmap") || t.contains("missing images");
}
```

命中即 `errorKind="dataset"`，我当时认为这是在防"训练器把 `--path` 判成不是 COLMAP 数据集"。

**推翻它的证据**：

- 这两个串在**新二进制里已经不存在**。team-lead 在 `native/` 源码树 grep 过，只剩旧日志和 README；
  native-brush 独立确认 `contains only ply files` 的唯一出处是被 commit `6060370` 删掉的 ViewSplats bail。
- 编译产物里也搜不到 → **这条规则永远匹配不上**，是死代码。

**替换后的口径**：见 §4.12.3。两个旧串**保留下来但改作 `errorKind="staleEngine"` 旧包探测器**——

`build/AttrTest.java` 直接对**编译产物** `PipelineManager.class` 反射调用
`looksLikeDatasetUnready()` / `looksLikeStaleEngine()` / `assertDatasetReady()`，
拿引擎的真实输出字符串做断言。理由就一句话：**规则看着对不算对，要拿编译产物真跑一遍断言。**
当前 15 项全 PASS，其中"旧串只命中 staleEngine、不再命中 dataset"这条是专门盯着这次死代码的。

#### 4.12.2 第二次：按报错条数硬拦 → 误杀成功任务

**原做法**：`Image not found` 出现 **≥2 次** → `errorKind="dataset"`，硬拦。

**推翻它的证据**（两条独立来源）：

- **源码层面**（team-lead 查的）：`native/brush/crates/brush-dataset/src/formats/colmap.rs:127-131`

  ```rust

  let Some((path, mask_path)) = find_mask_and_img(&vfs, &img_info.name) else {
      log::warn!("Image not found: {}", img_info.name);
      continue;
  };
  ```

  注释明说**缺图直接跳过、用剩下的继续训**——是设计意图，不是 bug。

- **实测**（native-brush）：从 `ds_44` 删掉 2 张（44 → 42）跑 5 步 → EXIT=0、`Image not found` 2 条、

**替换后的口径**：判据改为**视角数 N**（`Loaded N training views` 的 N），不看报错条数。
一句话概括：**N=0 拦、N>0 放行并提示**。

> 教训：未经实测的匹配串**本身就是误杀来源**，不是"多一层覆盖"。

#### 4.12.3 现行口径（`PipelineManager.java`）

native-brush 实测的四分类（同一数据集、同一新二进制）：

  | 场景 | 退出码 | 关键输出 | 处置 |
  |---|---|---|---|
  | 正常 | 0 | `Loaded N training views` + `Dataset provides initial splats` | 放行 |
  | **部分缺图（优雅降级）** | **0** | 若干 `Image not found` + `Loaded N training views`（N>0） | **只提示，放行** |
  | 缺 `images/` 到一张不剩 | **101（panic）** | `Image not found` ×N → `Loaded 0 training views` → `Need at least one view in dataset` → `Somehow lost data loading channel!` | `dataset`，硬拦 |
  | 旧二进制 | **1（bail）** | `Error: ... contains only ply files; a COLMAP dataset directory is required` | `staleEngine` |

- **教训一（死代码，详见 §4.12.1）**：我一度把 `Image not found` 出现 ≥2 次也判成 dataset。被源码注释 +
  实测双证据否掉：44 帧里删掉 2 张，引擎优雅降级（`Loaded 42`、EXIT=0、PLY 正常产出）。
  按条数拦会误杀本来能成功的任务。**区分"完蛋"和"能跑"的判据是视角数 N，不是报错条数。**
- 现行实现（`PipelineManager.java`）：
  1. `assertDatasetReady()` —— **训练前置体检**，在 `runTrain()` 入口执行：`dataset/images/` 至少一张图，
     `dataset/sparse/0/` 下 `cameras.bin`/`images.bin`/`points3D.bin` 存在且非空（0 字节的 bin 会让训练器
     静默拿到 0 视角）。缺任一直接抛「素材未就绪，训练无法开始」并列出缺项，`errorKind="dataset"`。
     → 与其把不完整数据集丢给训练器再回头猜 stderr，不如启动前自己验。
  2. `looksLikeDatasetUnready()` → `errorKind="dataset"`，**硬拦**。判据只有一个：**视角数 N**。
     用正则 `loaded\s+(\d+)\s+training views`（`CASE_INSENSITIVE`，取最后一次出现的 N），
     **N == 0 才拦**；再叠加两条 panic 签名 `need at least one view in dataset` /
     `somehow lost data loading channel`（这两条出现时 N 必然也是 0，双保险）。
     用正则而不是子串，是为了大小写/空格变化也抓得到，且能拿到数字。
     文案明确"素材/抽帧环节没准备好……不是设备图形能力问题"，**绝不提 GPU**。
  2b. **N > 0 一律放行**，缺图只给降级提示（不拦）：日志「有 N 张画面未能读取，已用其余 M 张继续重建
     （引擎对缺图是设计上的优雅降级，结果可能不完整）。本次不会被拦下……」，**N 和 M 都显示出来**，
     让用户看到"少了几张但照样跑完了"而不是"失败"。
     N 用 `countMissingImages()`、M 用 `loadedViews()`，两者都在 **stderr 全文**里统计
     （`stderrTail()` 只截最后 4000 字，帧数一多会漏计）。
     → 一句话概括行为：**N=0 拦、N>0 放行并提示**。既不是"按报错条数拦"，也不是"永远不拦"。
  3. `looksLikeStaleEngine()` → `errorKind="staleEngine"`（旧包探测器）：
     `contains only ply files` / `contains only` / `colmap dataset directory is required`。
     新二进制里已不存在，出现即说明装的是修复前的旧引擎，文案"当前安装的引擎版本过旧，请更新应用"。
  4. `isEmulator()` 兜底 → `errorKind="gpu"`（仅当上面都没命中），另 `looksLikeGpuDriverCrash()` 对
     退出码 139/11（SIGSEGV）直接判 gpu。
- **归因顺序 = dataset → staleEngine → gpu**，能定位真因的一律排在"设备不支持"之前。
- **回归测试**：`build/AttrTest.java` —— 对编译产物 `PipelineManager.class` 直接反射调用
  `looksLikeDatasetUnready()` / `looksLikeStaleEngine()` / `assertDatasetReady()`，
  用 native-brush 给的真实输出做断言（15 项，当前 `RESULT: PASS`）。这条测试存在的理由就是前两版规则
  先成了死代码、又差点误杀：光看代码"像对的"不够，得拿真实字符串跑一遍。

  ```bash

  AJ="$LOCALAPPDATA/Android/Sdk/platforms/android-36.1/android.jar"
  ```

`Image not found ×2 + Loaded 42` → 放行 / `Image not found ×2 + Loaded 0` → 拦 /

#### 4.12.4 适用范围声明

- **本节所有匹配串/正则判据只对当前这版 `libbrushheadless.so` 成立**。引擎一改措辞就失效——
  这正是 §4.12.1 那条死代码的成因。换引擎后请**重跑 `AttrTest`**，不要只看代码"像对的"。
- **`plyFraming()`（§4.8）不受本节影响**：取景归取景、失败归因归归因，两条链路不共享任何判据，
  也没有共用常量。
- **与 `scale_*` 相关的坑对 §4.8 的取景实现不成立**：`scale` 要 `exp()`、`opacity` 要 `sigmoid`、
  含半径后 bbox 膨胀 2–5 倍、建议改用 p99 —— 这些都是针对"会读 `scale_*`"的实现说的。
  我们的 `plyFraming()` 只读 x/y/z 位置（按 header 顺序累加 stride 定位），算质心 + 分轴 p95，
  全程不读 `scale_*`、不 exp、不用 min/max；渲染侧的 PLY→GLB 交给打包进
  `assets/runtime/dist` 的 splat-transform 官方库，log-scale/logit 还原是它的职责
  （**这条已由 native-sfm 读源码核实**，见 §4.8.1，不再是假设）。
  另：取景**不能用库自带 bound** 替代（库内含半径，会被 tail 撑大 2–5 倍），理由见 §4.8.1。
  所以 §4.8 / native-sfm §9.5.3 那组 3.65× / 4.12× 与入画率 97.4–98.4% **是独立成立的**，
  不受后来那一串尺度分析（包括 native-sfm 那个单位错误）的牵连。
  **别照着那些结论去改一个本来对的实现。**

### 4.13 真机排查顺序：先验字节，再验环境，最后才动算法

真机上一旦 SfM 跑出奇怪数字，**第一个要排除的是"打进 APK 的是不是我验证过的那份字节"**。
但那时模拟器大概率还是坏的、没法临时对比，所以基准值必须先存在这里（native-sfm 提供并复核）：

| 文件 | 字节 | sha256 |
| --- | --- | --- |
| `native/prebuilt/arm64-v8a/libiii_sfm.so` | 7,051,920 | `719e87bc0f04434dabb2aea6accb9e670b12a20e38a04b8ac9ed568b73311dcc` |
| `native/prebuilt/x86_64/libiii_sfm.so` | 24,809,256 | `40f194008eb12c7b62760ee85772765e2d13d1d7772921f69f3070abb0848a00` |

两个训练器的基准见 §1 的表（arm64 `3ac04ee0…` / x86_64 `bcc55740…`）。
**设备端核对命令**：`adb shell ls -l` 看字节数（arm64 trainer 必须 = **70,867,320**）；
要核 sha256 就 `adb exec-out run-as com.diandi.gaosi cat .../libiii_sfm.so | sha256sum`。

**排查顺序（native-sfm 给的，按此执行，不要跳步）**：

1. **先确认 APK 里的 `libiii_sfm.so` sha256 对得上** —— 对不上就是打包问题，**直接停**，不要往算法里查。
2. 对得上再看 **kill / exit code**：非 0 多半是**环境问题**（权限 / 路径 / SELinux），不是算法。
3. 还是正常但**数字不对**（注册帧数、点数、重投影误差异常），才可能是 **arm64 这条 ABI 首次被执行**
   的问题 —— 把 dev 日志给 native-sfm，按两个 ABI 逐段对比
   **SIFT 数 / 匹配数 / 初始对 / 每帧 PnP 内点数** 来定位，**先别急着改代码**。

> **首次观测声明**：arm64 那份 `libiii_sfm.so` **从未在任何 arm64 设备上执行过**
> （native-sfm §8.3 的验证边界）。所以真机第一次跑出来的数字**哪怕合理，也应记成"首次观测"而不是
> "理所当然"**；如果注册帧数和 x86_64 那版在同一组输入上不一致，那本身就是值得记录的发现，
> **不一定是 bug**。
